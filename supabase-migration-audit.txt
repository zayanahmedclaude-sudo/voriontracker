Project: Vorion Tracker
Repository root: voriontracker/
Audit basis: static repository inspection only; no database or external services were accessed.
Classification: CONFIRMED means demonstrated by repository code. ASSUMPTION means it requires runtime/database verification.

==================================================
1. EXECUTIVE SUMMARY
==================================================

CONFIRMED

This project is moderately, but critically, dependent on Supabase. Most application data access already uses the PostgreSQL "pg" driver through DATABASE_URL, not Supabase's data API. Supabase remains on the critical path for:

- Password verification and Supabase Auth administration.
- User creation, invitation, verification, password reset, disable/ban, and deletion.
- A browser Supabase Realtime postgres_changes subscription for employee_status.
- An Electron Supabase Realtime broadcast subscription for security-policy refresh.
- Server-side policy-update broadcasts through Supabase Realtime REST.
- Deletion of legacy objects from the Supabase Storage "screenshots" bucket.
- Deletion/retention compatibility for historical Supabase screenshot URLs.

Changing DATABASE_URL alone is not sufficient. It may move the direct SQL workload, but login and user management will still require Supabase Auth; two Realtime flows will still use Supabase; old Supabase Storage objects will still require access; and public/application IDs must continue matching Supabase Auth user UUIDs.

The main risks are:

1. Authentication continuity. public.profiles.id is deliberately populated with the Supabase Auth user UUID. Moving profiles without preserving IDs breaks nearly every employee foreign key.
2. Undocumented production schema drift. Several tables are queried or altered but are not fully created by scripts/migrate.js. Runtime code performs lazy DDL. The repository is not a complete, authoritative schema.
3. Weak tenant isolation. No organization/company table, organization_id, repository-defined RLS policy, or tenant-scoped JWT claim exists. Most privileged roles can query all rows.
4. Credential exposure. A deployment document contains a committed database password and agent/src/embedded-config.ts contains a committed Supabase public JWT. Values are [REDACTED] here and must be rotated/revoked as applicable.
5. Authentication/session design. Supabase verifies passwords, then the application issues its own 30-day JWT. The custom JWT is persisted in browser localStorage and a plaintext Electron JSON store, has no refresh/revocation/session table, and can retain stale roles.
6. Media migration. Current objects are primarily in Vercel Blob, while legacy screenshot rows can reference Supabase Storage. URL columns mix provider URLs with object identity.
7. Serverless connections. lib/db.ts creates one pg.Pool per runtime process with default pool sizing and no explicit SSL, timeout, or max-connection controls.

Supabase features in use:

- Supabase Auth: heavy and migration-critical.
- Supabase Realtime: two small but active use cases.
- Supabase Storage: legacy compatibility/deletion only in the inspected current upload flow.
- Supabase PostgREST/data API: not found.
- Supabase RPC/Edge Functions: not found.
- Supabase RLS definitions: not found in the repository.
- Supabase database: DATABASE_URL is expected to point to PostgreSQL, but the provider cannot be proven from code alone.

Recommended order:

1. Freeze schema changes and export the actual database catalog.
2. Establish an authoritative versioned PostgreSQL schema and reconcile drift.
3. Add tenant/organization boundaries before commercial multi-company use.
4. Prepare private PostgreSQL and a VPS-hosted backend/API boundary.
5. Migrate public application data with UUIDs unchanged while temporarily retaining Supabase Auth.
6. Normalize/migrate media metadata and copy legacy Supabase objects.
7. Replace Realtime with the existing Socket.IO service plus polling fallback.
8. Replace Supabase Auth with Better Auth backed by PostgreSQL, using a forced-password-reset transition unless password-hash portability is proven.
9. rebuild and deploy the Electron agent.
10. Remove legacy Supabase Storage and finally disable Supabase.

Estimated complexity: HIGH.

Supabase can be removed completely, but not by a database URL change. A staged migration is substantially safer than an all-at-once cutover. The safest interim state is self-hosted application PostgreSQL plus retained Supabase Auth, with stable user UUID mapping.

7. SUPABASE AUTH AUDIT
==================================================

Files:

- lib/supabase.ts - clients.
- app/api/auth/route.ts - password login and custom application JWT.
- lib/user.ts - create/invite/verify/reset/delete and status derivation.
- app/api/users/route.ts and app/api/users/* - admin lifecycle.
- app/api/supabase/resend-invite/route.ts - duplicate/legacy resend route.
- app/api/supabase/diagnostics/route.ts - privileged diagnostics.
- store/auth.ts and app/(auth)/login/page.tsx - browser login/persistence.
- agent/src/main.ts and renderer/App.tsx - desktop login/token persistence/logout.
- lib/auth.ts and lib/api.ts - custom JWT verification.

Flow:

- Login: backend calls Supabase signInWithPassword, checks confirmed_at/email_confirmed_at, loads public.profiles by email, enforces context/role, then signs a separate 30-day HS256 application JWT.
- Registration/self-signup: not found. Administrators create/invite users.
- Creation/invitation: Supabase admin createUser/inviteUserByEmail/updateUserById; profile is inserted with identical UUID.
- Verification/invitation email: Supabase generateLink/invite APIs and optional nodemailer fallbacks.
- Password reset: Supabase generateLink(type=recovery).
- Logout: local client token deletion only; no server session revocation.
- Middleware: does not protect auth; each API route is expected to call requireAuth.
- Server user retrieval: custom JWT plus public.profiles; Supabase session cookies are not used.
- Metadata: full_name, role, temporary password, banned flags are written into user_metadata. Storing a temporary plaintext password in user metadata is a Critical design flaw because metadata may persist and be readable through Auth APIs.
- Role authority: application authorization uses role copied into custom JWT and profiles.role. Supabase metadata is used mainly for user lifecycle/status, not route authorization.
- JWT claims: sub, role, teamId, name. No organization/tenant, session ID, token version, issuer, audience, or jti.
- Desktop token: custom application token is written to worktrack-store.json and restored at startup. No Supabase refresh token is stored because Supabase's returned session is discarded.
- Browser token: persisted by Zustand in localStorage under worktrack-auth.

public.profiles does not declare an FK to auth.users in repository DDL, but its IDs are intentionally synchronized with auth user UUIDs. No signup trigger creating profiles was found.

Password migration:

- Supabase Auth password hashes live in its managed auth schema; the repository does not expose them.
- Whether pg_dump access includes usable hashes is a human/provider question. Copying the whole Supabase auth schema into a custom system is not recommended.
- Existing passwords can only be preserved safely if the selected auth library supports the exact imported hash format and a reviewed rehash-on-login transition.
- Default recommendation: preserve user UUID/email/status, create replacement accounts, invalidate all sessions, and require a one-time password reset. Do not email plaintext temporary passwords.

Option comparison:

1. Better Auth with PostgreSQL
   Best fit. It provides database-backed users, accounts, sessions, verification and reset flows, and can integrate with Next.js. It replaces the insecure custom 30-day bearer session. Requires schema mapping and Electron bearer/session strategy.

2. Auth.js/NextAuth with PostgreSQL
   Viable for the web dashboard, especially OAuth or email flows. Credentials/password management is less turnkey and desktop/API bearer session integration needs more custom work.

3. Custom authentication using a proven library
   Possible with audited password hashing, opaque session tokens, rotation, email verification, reset, rate limiting, and device sessions. Highest implementation/security burden; not recommended unless Better Auth cannot meet Electron requirements.

4. Retain Supabase Auth temporarily
   Strongly recommended as a migration stage. It reduces simultaneous cutover risk. The backend can query the new PostgreSQL while Supabase continues credential verification; UUIDs must remain unchanged.

Recommendation: temporarily retain Supabase Auth while moving/reconciling application PostgreSQL, then adopt Better Auth with PostgreSQL and opaque/revocable sessions. Force password reset unless a separate proof-of-concept confirms safe hash import. Do not build hashing/session management from scratch.

17. VERCEL AND SERVERLESS COMPATIBILITY
==================================================

Current state:

- Vercel route handlers connect directly through DATABASE_URL via pg.Pool.
- A self-hosted VPS database that is "not publicly exposed" cannot be directly reached by ordinary Vercel functions without a private networking product/tunnel or public restricted TLS endpoint.
- Vercel outbound IPs are not inherently stable for a simple firewall allowlist unless a static-egress feature is purchased/configured.
- Default pg pools across cold starts/scale can exceed PostgreSQL max_connections.
- No explicit sslmode/CA verification, max pool, timeouts, or PgBouncer is in code.
- Cross-region latency would affect nearly every API call and multi-query report.
- IPv4 egress/support and VPS DNS/AAAA behavior must be verified.

Architecture comparison:

A. Vercel -> VPS PostgreSQL directly over restricted TLS
   Pros: fewest code changes.
   Cons: DB needs an internet-reachable TLS endpoint or private tunnel, static-egress/firewall solution, PgBouncer, strong CA verification, and tight roles. Violates the simplest interpretation of "not publicly exposed." Acceptable only as a controlled temporary bridge.

B. Vercel -> VPS backend API -> private PostgreSQL
   Pros: PostgreSQL remains Docker-private; stable connection pools; central auth/tenant enforcement; clean agent API; easier background jobs and backups.
   Cons: requires extracting/moving route logic or deploying compatible Next.js route handlers/API service on VPS; Vercel-to-VPS latency remains but fewer DB round trips cross it.
   Recommendation: safest practical target while retaining Vercel frontend.

C. Entire Next.js application/backend on VPS
   Pros: lowest DB latency, private networking, simple pooling/cron, no split backend.
   Cons: broader deployment/operations/CDN migration; changes current Vercel workflow.
   Good later option.

D. Keep Supabase temporarily
   Pros: lowest immediate risk while schema/auth/storage are disentangled.
   Cons: ongoing dependency/cost and split control plane.
   Strongly recommended as a staged transition, not final architecture.

Recommended: B. Host the authenticated backend/API, Socket.IO, workers, and PgBouncer on the VPS/private Docker network; keep static/Next.js frontend on Vercel initially. Browser and Electron call the VPS API over HTTPS. If Next.js server components/routes remain on Vercel, proxy them to the VPS API rather than exposing PostgreSQL.

PgBouncer:

- Use transaction pooling between backend and PostgreSQL.
- Backend pool should be deliberately small.
- Migration/admin connections bypass PgBouncer through a private direct DSN.
- If Vercel directly connects during transition, PgBouncer is mandatory and TLS/firewall controls must be reviewed.

21. PG_DUMP AND PG_RESTORE REQUIREMENTS
==================================================

Recommended format: custom (-Fc) for selective, parallel-capable restore and catalog inspection. Also save schema-only SQL for review. Run a separate globals/role inventory without restoring provider roles blindly.

Proposed reviewed examples using placeholders only:

pg_dump --format=custom --no-owner --no-acl --schema=public --file=[DUMP_FILE] [SUPABASE_DATABASE_URL]
pg_dump --schema-only --no-owner --no-acl --schema=public --file=[SCHEMA_FILE] [SUPABASE_DATABASE_URL]
pg_restore --list [DUMP_FILE] > [TOC_FILE]
pg_restore --no-owner --no-acl --role=[DATABASE_USER] --dbname=[VPS_DATABASE_URL] [DUMP_FILE]

For a low-downtime rehearsal, split:

pg_dump --schema-only --no-owner --no-acl --schema=public [SUPABASE_DATABASE_URL]
pg_dump --data-only --format=custom --no-owner --no-acl --schema=public --file=[DATA_DUMP_FILE] [SUPABASE_DATABASE_URL]

Review requirements:

- Include public tables, sequences, constraints, indexes, views, functions, and triggers that are application-owned.
- Exclude provider schemas by default: auth, storage, realtime, extensions, graphql*, vault, pgsodium, supabase_functions, net, cron unless an explicitly required custom object is found.
- Do not restore source owners/ACLs. Precreate target roles and assign ownership intentionally.
- Preinstall pgcrypto before objects that use gen_random_uuid().
- Large objects: none demonstrated; query pg_largeobject_metadata. Include only if used.
- Auth: export a minimum approved user mapping/status dataset separately. Do not import Supabase refresh tokens. Password hashes require a dedicated reviewed plan.
- Storage: export storage object metadata/manifests separately; pg_dump does not copy object bytes.
- Restore order: extensions -> schemas/types -> tables/sequences -> data -> sequence setval -> constraints/FKs -> indexes -> functions/views/triggers/policies -> grants.
- Roles: migration_owner, app_runtime, reporting_readonly, maintenance_worker, backup.
- Disable application writes during final data copy rather than globally disabling triggers without review.
- After restore, ANALYZE; validate sequences, FKs, row counts, timestamp ranges, and application reports.

If the source database is newer than target, pg_dump client should normally be same/newer compatible version and restore must be rehearsed. Never paste credentials into shell history; use protected password files/secrets.

23. SECURITY FINDINGS
==================================================

CRITICAL

1. DEPLOY.md contains a committed PostgreSQL password [REDACTED].
   Impact: anyone with repository/history access may access the associated database if still valid.
   Action: rotate immediately, remove from current file and Git history under an incident-reviewed procedure, audit access logs.

2. lib/user.ts writes the administrator-supplied temporary plaintext password into Supabase user_metadata.
   Impact: credentials can persist in Auth records and be visible through administrative/user metadata surfaces.
   Action: stop storing/emailing plaintext passwords; use single-use, expiring setup/reset links; purge metadata and rotate affected passwords.

3. No organization/tenant boundary exists.
   Files: schema/migrations and most API queries.
   Impact: deploying multiple companies under current roles can expose all monitoring data to privileged users.
   Action: do not market as multi-tenant until organization FKs, backend filters, tests, and preferably RLS exist.

HIGH

4. Custom bearer JWT lasts 30 days with no server session/revocation.
   Files: lib/auth.ts, store/auth.ts, agent/src/main.ts.
   Impact: stolen tokens remain usable; role/status changes may not revoke access.

5. Browser stores bearer JWT in localStorage; Electron stores it in plaintext JSON.
   Files: store/auth.ts, agent/src/main.ts.
   Impact: XSS/local-user/malware extraction.

6. Supabase service-role key has broad bypass capability.
   Files: lib/supabase.ts and callers.
   Impact: compromise bypasses RLS/Auth/Storage boundaries. It is server-only in inspected source, but diagnostics and operational handling increase risk.

7. Permanent/public-style media URLs are stored and returned directly.
   Files: screenshot/recording routes and metadata.
   Impact: copied URLs can bypass later application authorization; legacy Supabase parser explicitly uses public bucket URLs.

8. Application database role appears to use a single DATABASE_URL for DDL and runtime.
   Files: lib/db.ts, lazy schema code.
   Impact: runtime compromise can modify schema/data broadly.

9. Runtime lazy DDL and incomplete schema source of truth.
   Files: lib/schema.ts, lib/security.ts, lib/export-access.ts, live request route.

10. Serverless in-memory login limiter.

11. Cross-tenant-ready LiveKit/media authorization is absent.

MEDIUM

26. FINAL RECOMMENDATION
==================================================

Do not migrate everything at once.

Recommended architecture:

- Vercel may retain the frontend initially.
- Host authenticated backend APIs, Socket.IO, retention workers, PgBouncer, and PostgreSQL 16 on/near the Ubuntu VPS.
- Keep PostgreSQL on a private Docker network and never expose port 5432 publicly.
- Temporarily retain Supabase Auth while moving and reconciling public application data, preserving user UUIDs unchanged.
- Replace Supabase Auth in a later controlled phase with Better Auth backed by PostgreSQL, revocable database sessions, OS-keychain desktop storage, and forced password reset unless a hash-compatibility proof succeeds.
- Keep Vercel Blob temporarily to reduce scope, but convert metadata to bucket/object_key and serve private short-lived signed URLs. If full vendor removal is desired, migrate to private S3-compatible storage afterward.
- Replace both Supabase Realtime flows with the existing Socket.IO service and polling recovery.
- Point LiveKit server configuration to wss://live.vorionsystems.com and rebuild Electron to remove the embedded cloud URL/Supabase client.
- Introduce organization boundaries before multi-company production use.
- Use rehearsed initial load plus maintenance-window final delta; keep source read-only during a defined rollback window.

Biggest risk: identity and authorization continuity. Profiles and virtually all employee data depend on Supabase Auth UUIDs, while the current custom 30-day JWT and lack of tenant isolation make a rushed Auth cutover unsafe.

First five engineering actions:

1. Rotate the committed database credential, remove plaintext temporary-password metadata behavior, and open a security incident/history-remediation task.
2. Export the live PostgreSQL catalog and data inventory (including policies/functions/triggers/extensions/auth/storage metadata) and reconcile it against this code-derived schema.
3. Freeze runtime DDL and create a versioned baseline migration that reproduces the verified production schema.
4. Decide the backend placement/object-store/Auth-password-reset questions, then build a staging PostgreSQL/PgBouncer/private API environment with tested backups.
5. Rehearse public-schema migration with UUIDs unchanged while Supabase Auth remains active; run the complete validation and authorization checklist.
